# GaryHub 固定更新流程

## 每次启动

读取 AGENTS.md、PROJECT_CONTEXT.md，执行：

```bash
python scripts/updater/manage.py context
python scripts/updater/manage.py plan --base <本次实际审阅的基础提交>
```

先核对当前 Git 状态及远端最新分支，记录基础提交。需求未涉及的源码、旧发布目录、vendor bundle 无需重新读取。当前入口依赖 Python 3.9+ 和 Git；Windows 安装及 push 包可继续只使用 PowerShell、Git、OpenSSH。

## 开发与测试

1. 用独立分支开发，保留已有工作。按项目档案定位相关模块。
2. 对照现有实现确定行为变化，再选择测试。`plan` 给出影响范围与建议，不自动修改文件或运行全部测试。
3. UI 改动检查相关页面、手机布局和实际交互；账号/权限/数据写入改动增加身份、CSRF、并发、隔离与持久化检查；部署器改动增加备份、失败恢复、回滚和包哈希检查。
4. 默认检查既有测试中与变化相关的部分。小改动不复制整套历史测试；相关测试一次通过后不反复运行。上服务器前仍须保留版本核对、数据备份、健康检查和适用的隔离验证。
5. 文档或仓库工具调整不自动升级应用版本，也不触发生产站内通知。
6. 资源校验先确认访问条件：公开资源可校验未登录 HTTP 正文；受登录保护的页面须分别验证未登录跳转和文件完整性，并在隔离环境验证已登录响应字节。不得把 302 响应或登录页当作应用文件比较，也不能通过取消登录保护来让哈希通过。涉及上线校验时，应对真实 HTTP 响应执行实际校验器，不能仅让模拟网络函数返回期望文件内容。

检查通用入口及清单：

```bash
python scripts/updater/manage.py check
python -m unittest discover -s scripts/updater/tests -p 'test_*.py'
```

## 发布清单与打包

`releases/current.json` 是源码版本入口；`releases/<version>.json` 记录基础版本、能力组合、适配器、必要保护及验证记录路径。它们不保存生产凭据，也不代替服务器现场状态。

```bash
python scripts/updater/manage.py build --release 1.4.3.2 --output <ZIP绝对路径>
```

统一入口验证清单并调用该版本自己的已审阅适配器。当前 v1.4.3.2 使用独立 release-config.json 与共享 build_overlay.py、deploy_runtime.py；历史适配器保留原状。未来发布须注册自己的清单和小型适配器，明确审阅基础提交、实际基础版本、能力组合和必要检查。禁止仅换版本号后运行旧部署器；修改共享实现须保留既有保护测试并验证兼容性。

生成 ZIP 的内容仍为：Windows 安装入口、回滚入口、校验清单、应用变更、源码同步和说明。每包独立可用，用户无需保留旧包。打包前完成必要验证，生成最终包后校验一次内容及哈希；只有内容变化时才重建。

## 根 README 同步检查（每次发布必做）

根目录 `README.md` 是当前项目入口，不能只在末尾追加新版本而保留过期的“当前正式状态”。每次发布在最终打包前检查：

1. 源码版本与 `releases/current.json` 一致；更新本次相关功能、入口、使用边界及文档链接。
2. 明确区分源码准备、本地验证、GitHub 合并和生产验证；缺少现场证据时不得宣称已上线，也不能把旧上线版本写成最新源码版本。
3. 安装基线、双击安装／回滚／源码同步入口、构建示例指向本次发布；链接存在且不指向过期适配器。
4. 当前 Compose、镜像与宿主挂载路径以有效部署索引和现场证据为准。把早期具体路径、镜像 ID、用户数量等移到或链接至明确标注的历史记录，避免继续作为当前操作指令。
5. 新版本特性以实际源码与验证记录为依据。无关条目可保留，但必须记录已检查 README 是否仍准确；保留私密数据与密钥不入库的规则。

`AGENTS.md` 只保留此检查的入口提醒；长期流程由本文件维护。本次版本说明记录具体改动，不代替长期要求。

## 安装现场

按顺序：核对实际版本/能力/有效 Compose → 基于现有镜像离线构建 → 必要隔离测试 → 数据与私有配置备份 → 切换 → HTTPS/健康验证 → 按 RELEASE_POLICY 发布并核对通知 → 记录结果。

版本、源码或配置不匹配时停止，提供精简报告，取得现场证据后调整兼容规则。不要跳过校验或将未识别版本纳入任意兼容范围。回滚检查后续部署情况并保留当前用户记录。回滚完成前必须核对容器实际镜像和 Compose 路径标签，将部署索引对齐实际恢复路径，并执行下一次升级使用的严格一致性检查。测试应包含“失败切换→自动回滚→再次升级预检”的连续流程；模拟 Docker 时须记录实际 -f 路径标签，不能仅模拟镜像 ID。历史遗留索引只允许在审阅过的回滚证据、配置内容和运行状态全部一致时原子对齐，不得忽略校验或任意采纳当前路径。

## 状态维护与交付

每次更新同步维护：根目录 README.md、PROJECT_CONTEXT、发布清单、版本说明和对应验证记录。状态分别记为源码已准备、本地已验证、GitHub 已合并、生产已验证。只有收到实际部署证据，才记录生产完成及通知人数。

GitHub push 包仅导入明确列出的源码文件，使用独立工作目录和审查分支；校验来源、补丁、变更范围与目标文件哈希，普通 push 后打开 PR 页面。不得 force push、覆盖用户未提交文件或自动合并 main。

## 以后给 AI 的短指令

先读取 AGENTS.md、项目档案和固定更新流程，将 Garyhub 从【基础版本】更新至【目标版本】。本次需求：【需求】。定位相关模块，复用统一入口和发布适配器，运行与变化相关的检查，更新档案与发布记录，最后生成可双击安装的 upgrade ZIP；成功日志给摘要，失败时展开相关日志。

如果只需要更新 GitHub，将最后一句改为“生成 GitHub push ZIP，不部署服务器”。
